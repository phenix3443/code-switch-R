# UI Reference Alignment

用于这类任务：

- 用户给了截图，并要求“照着这个布局改”
- 用户点名参考对象，例如 VS Code、某个官网详情页、某个扩展页面
- 用户反复指出“没对齐”“太丑”“信息重复”“你自己先 CR”

## 核心原则

先对齐结构，再微调视觉。

这里的“对齐”优先级如下：

1. 信息架构
2. 分区顺序
3. 标题和计数的位置
4. 操作入口的位置和类型
5. 间距、分割线、密度
6. 图标与文案
7. 最后才是配色或局部风格

不要一边参考 VS Code，一边擅自改成卡片式后台页。参考对象如果是高密度工具界面，就按高密度工具界面处理。

## 必做检查

开始改之前，先明确这 4 件事：

- 哪些是参考界面的固定结构，必须保留
- 哪些是当前产品域模型里的真实信息，需要映射进去
- 哪些内容现在是重复展示，应该删掉一处
- 哪些功能还没做完，只能保留入口壳

## 实施顺序

1. 先列出参考界面的结构骨架。
2. 把当前页面逐块映射到这个骨架。
3. 先删重复块，再改样式。
4. 未实现功能只保留最小入口，不伪装成完整主流程。
5. 改完后自己重新审一遍实际效果，再继续下一轮。

## 当前项目调试流程

这个仓库里，前端视觉改动后不允许只靠代码阅读或构建结果收尾，必须做实际界面 CR。

默认流程：

1. 启动测试实例：

```bash
make test-app
```

2. 确认前端调试地址。优先看：

```bash
tail -n 80 .tmp/test-home/.code-switch/test-app.log
```

从日志里找 `Local:`，通常是 `http://127.0.0.1:9255/` 或 `http://localhost:9256/`。

3. 打开目标页面做实际检查。Skills 页默认使用：

```text
http://127.0.0.1:<vite-port>/#/skill
```

4. 每次修改后都要重新截图或重新查看真实页面，不允许只说“理论上应该对了”。

5. 如果页面没刷新到最新状态，先硬刷新再继续看。

## Skills 页面专项约束

如果是本项目的 `frontend/src/components/Skill/`：

- 左侧列表优先参考 VS Code Extensions：分组标题、计数、折叠箭头、搜索区、行内操作都要先对齐结构
- 默认使用细线分割和扁平列表，不要回退成大圆角卡片
- 详情区展示“选中 skill 的完整信息”，不要重复列表里已经表达过的摘要
- `Claude` / `Codex` 安装入口应放在与该 skill 强相关的位置，不要漂移到全局区域
- 推荐项的未完成操作优先放到齿轮或菜单壳里，不要先塞主按钮
- `Views` 子菜单优先保持参考对象的分组顺序和勾选位置；未实现过滤要做成占位提示，不要伪装成已生效

## 自查清单

完成后必须自查，不要直接交给用户：

- 分组标题是否和参考对象一样左对齐，是否有折叠箭头
- 标题、计数、操作图标是否在同一基线
- 是否还存在重复信息块
- 图标是否使用了用户指定的官方图标
- 详情区是否仍有“列表摘要的重复副本”
- 空状态、错误态、加载态是否被错误触发
- 当前效果是否真的更像参考对象，而不是只改了配色
- 这次是否已经实际打开页面做过 CR，而不是只跑了构建

## 禁止事项

- 未经用户要求，不要删掉用户特意保留的占位字段，如 `unknown`、`待配置`、`待开发`
- 不要把“结构没对齐”的问题误判成“样式不够花”
- 不要在用户要求精简时新增大块说明文字
- 不要自己脑补新交互替代参考对象已有交互
- 不要跳过实际界面 CR
